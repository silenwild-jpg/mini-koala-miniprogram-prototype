# CAP-UNIT-DUAL-01｜平方米双单位需求及展示契约（2026-11-12）

## 产品裁定
- 当前阶段是 HTML/Web 产品原型验证，不是微信原生小程序；演示场景允许受控模拟门店与优惠。不得把 CI 成功等同上线验收。
- 原有 CAP-FIRST、容量 0.5–200m³、租期 1–60 个月及 CAP→S5 双必选门禁保持。S01/S02 无需求继续按 PR #140 最低折后月租“起”口径。不得重新引入 S5 incomplete、U01、比较功能或额外面积筛选。
- CAP 容量输入区域增加 m³/㎡ 切换，初始仍为 m³，用户切换后该任务链路保留原始输入值。仅一位小数的 0.2–80㎡ 用于本轮原型估算，对应 0.5–200m³，后续可按产品参数重新裁定精度。
- 本轮输入估算的标准高度为 2.5m：输入面积 × 2.5 转为统一的容量匹配阈值。这仅是初步估算，不是所选仓位的实际面积，不能保证大件必然放入。尤其小于 3m³ 的仓高不同，不能倒推为统一 2.5m。
- 中央 requirement.capacity_m3 继续为推荐、报价与下单的唯一容量数值，requirement.input_unit/input_value 仅记录用户输入表达；所有优惠、折后最低起价、整期租金、押金/管理费、仓位ID和订单快照计算保持原逻辑。转换本身不改租期和金额。
- 仓位面积仅在 dimensions_m 或可靠 area 数值存在时显示“约 X㎡”；旧仓型尺寸空值时不猜测，也不为所有卡片强行加辅助标签。㎡用户的 S01/S02/S5 需求摘要为“2㎡ · 5m³ · 12个月”，不创建第二修改入口。
- 门店卡/仓位卡保留容量主视觉；只复用现有文案行表达面积，不增加新卡片、阴影或边框；H01 不新增面积任务卡；S01 三筛选、S5 两门店+考拉E存排列不变。
- 用户按面积输入并不能代表长宽和门宽适配已确认：需要大件搬运的场景仍走现有按物品估算或顾问路线。待接入真实库存时须基于长宽高和物品实际尺寸二次验证。

## QA 与归并
1. CAP: m³默认态、㎡合法/非法输入、单位切换、快捷容量、返回草稿、编辑旧需求、租期必选、50m³顾问阈值。
2. S01/S02：普通浏览起价不变；完整需求返回后呈现㎡+m³+租期；无尺寸运营型选项不展示假面积。
3. S5：从 CAP、物品估算、S01/S02、深链和“查看更多”回流；面积意图不可绕过租期门禁；两推荐仓位卡与考拉E存结构冻结。
4. O01：价格/优惠、仓号、押金、管理费、手机号验证、支付及订单快照维持 m³ 的现有签名与规则。
5. 375×812、390×844 浏览器与键盘操作截图，关注 CAP 输入行、S01 描述、S02 规格、S5 摘要是否折行遮挡。
6. 只接受同一 SHA 的真实自动化测试结果。自动化通过后依旧 Draft/HOLD，须用户人工视觉签收才可归并；不部署 Netlify、不自动合并 main。
