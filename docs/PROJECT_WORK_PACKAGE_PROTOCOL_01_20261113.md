# PROJECT-WORK-PACKAGE-PROTOCOL-01｜批量任务与交付协议

**用途：** 让一个明确目标在一次任务包内连续完成可授权的盘点、实施、验证、文档和状态回写，避免把每个微小动作拆成多轮等待。
**适用：** 迷你考拉仓 Web/HTML 演示原型、视觉/交互迭代、QA、仓库治理与文档任务。
**优先级：** 高于历史登记表中的旧式逐项确认流程；不覆盖用户最新产品规则和高风险操作授权边界。

## 1. 工作包结构

- **一个完整目标 = 一个 GitHub Issue / 工作包。**
- **一个工作包 = 一个主要实施分支 + 一个主 PR。**
- 可在同一分支内进行多个阶段提交；不要把一个连续目标拆成多个微型PR。
- 同一目标的独立QA、文档归档若确实需要隔离，可建立辅助PR，但必须引用主工作包，并明确说明为何不能合并到主PR。
- 开始前先读取项目控制中心，冻结基线SHA、当前规则、页面归属、验收门槛和授权范围。

## 2. 批量执行规则

任务包启动后，连续执行所有已批准且不依赖用户决策的子任务：

1. 读取基线、规则和相关历史证据；
2. 盘点任务范围与依赖；
3. 拆分可并行/可串行子任务并建立 Issue checklist；
4. 实施所有已批准改动；
5. 运行范围内自动化与浏览器验证；
6. 对同一候选SHA执行完整回归；
7. 整理截图、日志、Artifact、文件差异和回滚点；
8. 更新控制中心、任务Issue和PR描述；
9. 在具备授权且门禁通过时完成治理归并；否则明确保持HOLD。

**不得**每完成一个小步骤就等待用户发送“继续”。遇到阻断项，只暂停依赖该决策的部分，无关任务继续。

## 3. 仅以下情形需要暂停并请求确认

| 阻断类型 | 例子 | 处理 |
|---|---|---|
| 产品决策冲突 | 两条已批准规则互相矛盾，且无法按最新决策/页面契约裁定 | 只暂停冲突页面/路径 |
| 冻结视觉或核心交互变更 | 新增CTA、改变导航层级、改动获批母版结构 | 提交对比稿并请求明确批准 |
| 生产政策无法隔离 | 真实价格、法律协议、实名/支付规则会影响演示路径且无可替换演示方案 | 保留演示可用路径，单独登记业务责任方 |
| 权限缺失 | 无法读取/修改目标资源，或需要管理员操作 | 说明缺失权限和最小用户动作 |
| 不可逆/高风险操作 | 删除分支、批量关闭PR、改变权限/Ruleset、合并业务候选、正式部署 | 先给具体对象清单和影响，取得明确授权 |
| 验收证据不足 | 同SHA证据缺失、来源不明、人工视觉未签收 | 标记HOLD，不伪造PASS |

## 4. 演示阶段与生产阶段分离

- 演示优先保证真实用户路径、完整界面状态、可操作交互、跨页状态一致和稳定可复现。
- 缺少真实门店、库存、地图、CRM、支付或最终业务规则，不自动阻断前端；采用可替换演示配置并登记待业务/后端确认事项。
- 不在普通消费者界面暴露“模拟/演示/内部”解释性文案。
- 不把临时演示配置描述为正式生产政策。
- `DEMO READY`、`DEMO PREVIEW DEPLOYED`、`PRODUCTION READY` 是三个独立状态，不得互相替代。

## 5. 固定状态机

每个交付项必须使用以下状态之一：

`APPROVED → IMPLEMENTED → TESTED → VIS_SIGNED → MERGED → DEPLOYED`

- `APPROVED`：范围和规则有明确依据；
- `IMPLEMENTED`：代码/文档已提交；
- `TESTED`：精确SHA的测试已运行并有证据；
- `VIS_SIGNED`：需要视觉验收的项目已由授权人签收；
- `MERGED`：PR实际合并；
- `DEPLOYED`：对应SHA/构建身份的部署已验证。

不适用的状态写 `N/A`；未完成写 `HOLD` 或 `NOT_TESTED`，不得跳级。

## 6. 每个工作包的固定交付字段

1. 当前阶段、工作包编号、基线SHA和候选SHA；
2. 本次修改文件、提交和PR链接；
3. 已实现的用户路径、页面状态和交互；
4. 375×812与390×844自动化/浏览器证据（不涉及UI则写N/A）；
5. 人工视觉签收人、日期和获批原图（不涉及视觉则写N/A）；
6. 演示数据/临时规则及其替换边界；
7. 待业务/后端确认事项：责任方、影响页面/流程、后续阶段；
8. 未测试、已知缺陷和真正阻断项；
9. 回滚Commit、归并状态、部署状态；
10. 下一工作包编号与唯一下一动作。

## 7. 验收与归并门禁

- 所有证据绑定同一个精确候选SHA；测试期间冻结分支写入。
- 代码/CI PASS不等于视觉签收；视觉签收不等于已部署。
- PR范围必须与Issue授权一致；治理文档PR不得夹带业务代码。
- 仅在必需检查通过、main base未发生未处理漂移、文件范围复核通过后，按既有授权合并治理PR。
- 业务候选 #176、历史PR关闭、分支删除、Ruleset/权限修改、Netlify配置和正式部署继续执行各自独立授权门禁。

## 8. 最小周转汇报格式

每次关键任务后只输出：

- **当前阶段：**
- **本次完成：**
- **遗漏/待确认：**
- **归并状态：**
- **下一步编号：**

细节和证据链接放在Issue/PR/控制中心，不在聊天中重复整份历史资料。
