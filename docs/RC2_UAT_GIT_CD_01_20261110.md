## 首次连接 Netlify，需账号持有人进行一次 GitHub 授权

在**已有的独立空站**操作，禁止误用旧RC1或RC2站。

1. 打开 <https://app.netlify.com/projects/mini-koala-rc2-uat-pr96-20261110>。
2. 进入 **Project configuration → Developer settings → Continuous deployment → Repository → Link repository**。
3. 选择 **GitHub**，仅授予本仓库所需访问权限，并选择 `silenwild-jpg/mini-koala-miniprogram-prototype`。
4. 将这个**独立UAT项目**的 **Production branch** 明确设为 `uat/rc2-pr96-20261110`，不是 `main` 或 `integration/rc2-rebaseline-01-20261110`；必要时在 **Branches and deploy contexts** 中改为这个分支。
5. Build command / Publish directory 以 UAT 分支根目录 `netlify.toml` 为准（避免被旧RC1 UI历史设置覆盖），如界面要求手动填写：
   - **Base directory** 留空（仓库根目录）。
   - **Build command** 使用 `netlify.toml` 的完整 `[build].command`。
   - **Publish directory**：`release-evidence/rc2-merge-prep-10/site`。
6. 不关闭现有 **Team SSO**；正式开展多用户UAT前另行安排合法访问许可。设置仅针对这个独立Netlify项目。
7. 连接后 Netlify 首次构建如果失败，先看 deploy logs 的源SHA与关口报错；**不得关闭冻结素材门禁或回退到RC1构建**。

## 后续受控升级顺序

1. 在开发候选分支修复问题，运行业务单测、375/390回归、人工视觉复核。
2. 只有批准下一候选后，更新UAT分支冻结 `app/` Git Tree、候选PR SHA和构建校验，再把获批原型的代码变更导入UAT分支。不得直接把尚未通过QA的 PR 开发分支作为Netlify发布分支。
3. 只向 `uat/rc2-pr96-20261110` 推送时，Netlify自动构建部署。GitHub Actions先验检查只是额外证据；**由Netlify自己执行的构建前版本门禁才是阻断未批准业务代码发布的关键保障**。
4. 每次测试记录部署ID、UAT提交、PR候选提交、实际测试者、证据和结论；原有两个Netlify历史站不应被覆盖。
5. `main` 归并保持HOLD，直到正式用户UAT和业务视觉终签。
