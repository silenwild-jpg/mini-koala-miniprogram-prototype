# DUAL-AGENT-GOVERNANCE-01｜ChatGPT × WorkBuddy 协作治理

**状态：** PROPOSED / Draft PR，待用户审阅批准  
**适用范围：** 迷你考拉仓项目在同一 GitHub 仓库内，由 ChatGPT 与 WorkBuddy 分工完成规则梳理、代码实施、独立评审和版本验收。  
**项目阶段：** 产品验证、Web 演示原型与视觉迭代；不代表微信原生小程序或生产系统已验收。

## 1. 治理目标

在共用 GitHub 仓库的前提下，建立可追溯、可复核、互不覆盖的协作方式。GitHub 是代码、提交、PR、自动化结果和证据的共同事实来源；聊天记录用于解释决策，不替代仓库中的正式规则与提交记录。

“共用仓库”不等于“共用工作区”或“自动同步上下文”。任何一方都必须通过精确分支、Commit SHA、PR 和可复核证据交接工作。

## 2. 角色与权限边界

### 用户（产品决策与最终授权）
- 决定产品规则、业务口径、冻结视觉方向及任务优先级。
- 对涉及冻结结构/交互、核心流程、业务政策的变更作最终裁定。
- 明确批准合并 main、部署、权限/保护规则变更及历史成果清理。
- 可要求任一方暂停、复核或撤销尚未合并的提案。

### ChatGPT（规则管理与独立评审）
- 梳理需求、维护规则解释、形成可执行任务说明和验收标准。
- 在 WorkBuddy 提交后，独立检查 PR diff、规则符合性、测试结果、375/390 截图及交互证据。
- 输出明确结论：PASS / PASS WITH NOTES / REQUEST CHANGES / BLOCKED，并列出证据与未覆盖范围。
- 不把 WorkBuddy 的自测结论直接当作独立验收；不凭截图推断代码或运行测试已经通过。
- 未经用户明确授权，不直接修改应用代码、不代替 WorkBuddy 推送其实施分支、不合并 main、不部署。
- 本任务中 ChatGPT 可建立治理文档提案；这不构成未来可自行修改业务代码的授权。

### WorkBuddy（代码实施与工程验证）
- 按已批准任务说明，在自己的工作分支实施代码、资源和测试脚本变更。
- 提交最小范围、可追溯的 Commit/PR，附修改前后截图、375/390测试和运行证据。
- 如遇规则冲突、缺少素材或无法验证的行为，标注 BLOCKED / NOT TESTED，不自行猜测产品决策。
- 不得自行修改已批准的产品/视觉基线，不得把建议或临时实现升级为正式业务规则。
- 不直接推送 main，不自行合并 PR，不部署，不删除历史分支或PR。

## 3. 分支与版本隔离

1. `main` 是受保护的已批准基线。双方均不得直接向 main 推送提交。
2. 每个实施任务使用独立分支，建议命名：`workbuddy/<TASK-ID>`。分支从任务批准时的最新 main 或用户指定的精确 SHA 创建。
3. ChatGPT 的评审以只读检查为默认方式；评审修订意见通过 PR Review / Issue /任务说明反馈，不直接改写 WorkBuddy 工作分支。
4. 不在其他 Agent 的分支上继续开发，不重置、强推或覆盖对方提交。
5. 任务基线必须记录：源分支、基线 SHA、工作分支、当前 HEAD SHA。验收绑定精确 SHA；任何新提交都会使该 SHA 的相关验收需要重新确认。
6. 若任务依赖一个尚未合并的候选 PR，必须明确选择：独立替代候选、经批准后以该候选为父基线，或等待候选先行处理。不得默认把未合并 PR 的改动悄悄带入新 PR，也不得擅自改写被冻结候选。
7. 历史分支、已签收 SHA、原始素材和证据包均按只读资产处理；清理必须单独授权。

## 4. 规则优先级与冲突处理

按以下顺序判断：
1. 用户最新明确裁定；
2. 当前有效项目控制中心及已批准/冻结规则；
3. 对应精确 SHA 的实现与测试证据（用于证明实现事实，不自动产生产品批准）；
4. 历史 PR、旧文档、旧截图和旧原型。

发现冲突时：
- 记录冲突双方的文件/规则、来源日期、影响页面与风险；
- 将冲突项标记为 NEEDS-DECISION / BLOCKED；
- 不以“代码已存在”“旧 PR 曾通过”或“实现成本较低”为理由覆盖用户最新决定；
- 不阻塞与该冲突无依赖关系的其他已批准工作。

## 5. 标准任务流

`PROPOSED → USER_APPROVED → IMPLEMENTING → PR_OPEN → TECH_CHECKED → INDEPENDENT_REVIEW → USER_ACCEPTED → MERGED`

- PROPOSED：提出方案，尚无实施授权。
- USER_APPROVED：用户批准明确范围、基线和验收要求。
- IMPLEMENTING：WorkBuddy 在独立分支实施。
- PR_OPEN：提交可审查的 PR，保留完整 diff。
- TECH_CHECKED：对应 SHA 的自动化/人工技术测试已执行并记录。
- INDEPENDENT_REVIEW：ChatGPT 完成独立规则、代码和证据评审。
- USER_ACCEPTED：用户批准该变更进入主线。
- MERGED：GitHub 确认已合并。

不得将以下状态混为一谈：代码已提交 ≠ 技术测试通过；技术测试通过 ≠ 视觉签收；视觉签收 ≠ 用户批准合并；合并 ≠ 已部署；Web 原型可运行 ≠ 微信原生小程序验收。

## 6. WorkBuddy 每个 PR 的交付清单

每个 PR 描述至少包含：

- 任务编号、目标和范围；
- 基线分支与精确基线 SHA；
- 工作分支与当前 HEAD SHA；
- 修改文件清单及每项修改原因；
- 对应产品/视觉/交互规则来源；
- 未修改范围与明确排除项；
- 375×812、390×844 两种视口的前后截图；
- 覆盖的页面状态、主流程和异常状态；
- 实际执行的命令、测试结果和可复核 Actions 链接；
- Console/网络错误检查结果；未执行项目明确写 NOT TESTED；
- 已知问题、业务/后端待确认项及回滚方式；
- 请求 ChatGPT 独立复核的具体问题。

不得伪造截图、测试日志、运行结果或 PASS 结论。截图应能追溯到对应 SHA 和视口。

## 7. ChatGPT 独立评审清单

评审至少核查：
1. PR 基线、HEAD SHA 与任务授权范围是否一致；
2. diff 是否只改任务范围，是否误删已批准页面、入口、状态或素材；
3. 是否遵守最新产品规则、VIS-GUARD 和演示优先原则；
4. 是否将待业务/后端确认事项错误写成正式生产政策；
5. 375/390 证据是否来自当前待审 SHA，是否覆盖关键状态；
6. 测试是否真正执行，是否存在只报告结果但没有证据的情况；
7. 视觉变化是否引入未经批准的卡片、边框、阴影、背景、导航或布局变化；
8. 是否有可回滚路径，是否存在影响其他页面的共享状态/组件副作用。

评审结论：
- **PASS**：范围、规则和证据满足本任务要求。
- **PASS WITH NOTES**：无阻断项，但存在已记录且不影响本轮目标的遗留事项。
- **REQUEST CHANGES**：有可修复的不符合项，修改后需重新评审。
- **BLOCKED**：缺少关键决策、权限或证据，当前无法可靠验收。

## 8. 不可自动执行的操作

除非用户对具体对象和动作作出明确授权，双方不得：
- 合并 main、部署站点或发布微信原生版本；
- 修改 GitHub Ruleset、分支保护、仓库权限或 Actions 安全设置；
- 删除分支、PR、Issue、历史文件、原始素材或证据；
- 改写已签收候选、冻结视觉母版或核心业务流程；
- 将演示 mock 数据、临时算法或待确认口径声明为生产规则。

## 9. 沟通与交接格式

每次交接使用简明结构：
- **任务编号 / 当前状态**
- **基线 SHA / 当前 HEAD SHA**
- **已完成**
- **未完成 / BLOCKED / NOT TESTED**
- **证据链接**
- **需要对方执行的下一动作**
- **是否需要用户裁定**

交接必须指向 GitHub 中可访问的文件、Commit、PR、Actions 或 Artifact，不以“已在聊天里说明”替代。
