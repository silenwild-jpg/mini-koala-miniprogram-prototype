## 0. 你的角色

你是这个项目的**编译与真机验证执行方**。项目是「迷你考拉仓」（自助仓储）的微信原生小程序，代码由另一方（下称「代码方」）编写和维护，产品负责人是张坤。

你要做的是：把工程导入微信开发者工具、编译到 0 报错、在模拟器和真机上跑通、上传并协助发体验版，然后**按第 8 节的格式回报**。

你不是这个项目的开发负责人。不要重构、不要补做未完成的页面、不要改业务规则。代码方会继续在自己那份基线上开发，你这边的改动越小，合并越不会出错。

## 1. 背景与现状（先读，再动手）

- 路线：微信原生（WXML / WXSS / JS，不用任何跨端框架、不用 npm 依赖、不用 TypeScript）。
- 数据：全部是本地演示数据（`core/config.js` 里 `DATA_SOURCE: 'mock'`），**运行时不发任何网络请求**，不需要配置服务器域名。
- 进度：35 个页面全部写过第一遍，没有占位页。各页做了哪些状态、哪些没做、哪些是代码方自定的做法，见 `docs/W34_Status.md`，**动手前先读它**。
- **这份代码从未在微信开发者工具里编译过，也没上过真机。** 代码方只做过：单元测试 147 项、静态检查、在 Node 里用假的 `wx` 对象模拟运行 6,522 次、用演示订单联调 960 次。这一版代码量约是 v0.1.0 的 5 倍，由多路并行写成，所以首次编译出现**成批、同类**的报错是预期之内的事，你的第一项任务就是把它们找出来并归类。
- 支付是演示：代码不调用 `wx.requestPayment`，不会扣款。登录后自带 5 笔覆盖各阶段的演示订单。
- `project.config.json` 里 `appid` 现在是 `touristappid`，基础库写的是 `3.5.8`。

## 4. 任务一：主工程导入、编译、验证

按顺序做，每一步的结果都记进回报。

**步骤 1　改代码前先留基线**
在交接包根目录执行 `git init && git add -A && git commit -m "baseline v0.2.0"`。之后你的每一处改动都单独提交，提交说明写清原因。最后用 `git diff baseline..HEAD` 导出补丁交回。

**步骤 2　先跑四项检查，确认交接包完好**（在交接包根目录运行，需要 Node 18 及以上、Python 3）
```
node --test tests/
python3 tools/static_check.py miniprogram
node tools/smoke_run.js miniprogram
node tools/smoke_orders.js miniprogram
```
预期结果：测试 147 项全部通过；静态检查 `"errors": []`、`"placeholders": 0`；模拟运行最后一行 `{"pages":35,"components":21,"handler_calls":6522,"errors":0}`；订单联调最后一行 `"errors":0`（其中订单号含当天日期，逐日不同）。模拟运行约需 2–3 分钟，过程中会打印若干 `{ code: 'NOT_FOUND' ... }`，那是失败分支的日志，不是错误。
四项里有任何一项与预期不符，**停下来回报**，不要往下做（说明包在传输中损坏，或你的环境有差异）。

**步骤 3　导入并编译**
- 微信开发者工具 → 导入项目 → 目录选 `miniprogram/`；记录开发者工具版本号和实际使用的调试基础库版本。
- 记录控制台里**全部**报错和警告的原文（不要转述、不要只记第一条）。
- 你能直接操作开发者工具的图形界面或命令行就自己做；做不到就把步骤告诉张坤，请他把控制台原文和截图贴给你。命令行工具的参数请以你本机 `cli --help` 的输出为准，不要凭记忆写。

**步骤 4　修编译和运行报错**（规则见第 5 节）
- 一次只修一类问题，修完重新编译，再跑一遍步骤 2 的四项检查。检查不过的修法不算数。
- **先归类再修**：同一种写法的报错通常会在多个页面重复出现，先列出类别和各自涉及的文件数，一类一类修，不要逐个文件零散改。
- 代码方事先能想到、但没有条件验证的风险点，请逐项确认并在回报里写结论：
  1. `app.json` 里的 `requiredPrivateInfos: ["getLocation"]`、`permission`、`__usePrivacyCheck__`、`lazyCodeLoading`、全局 `usingComponents` 在当前基础库下是否被接受；游客 AppID 下是否因此报错。
  2. tabBar 的 8 张图标路径、尺寸、体积是否合规。
  3. 5 个分包与 `preloadRule` 是否正常；主包和各分包的体积（开发者工具「代码依赖分析」里的实数）。
  4. 首页用了自定义导航栏的避让计算（`app.js` 里取胶囊位置）：模拟器和真机上标题区是否与胶囊对齐、有没有被状态栏遮住。
  5. WXML 里的表达式、`wx:for`、`wx:key`、组件属性与事件绑定有没有被编译器拒绝或给出警告的写法。
  6. WXSS 里的 CSS 变量（`styles/tokens.wxss`）和选择器是否有不被支持的写法；组件样式隔离是否导致样式丢失。
  7. `require` 路径、分包之间是否有跨包引用被编译器拒绝。
  8. `app.json` 开了 `style: v2`：`.mk-btn` 按钮的宽度是否正常（代码方在 `app.wxss` 里补了 `width: auto`，没验证过）。
  9. `docs/W34_Status.md` 末尾「最需要编译或真机确认的」6 类，逐类给结论。

## 5. 改动规则

**可以改（为了编译通过和真机正常，改动尽量小）：**
- 编译器明确拒绝的语法、路径、配置项。
- `project.config.json` 里的 `appid`、`libVersion` 和开发者工具自动写入的本地设置。
- 明确的运行时报错（例如某个 `wx` 接口的参数或返回与真实环境不一致）。

**不可以改，遇到就停下回报：**
- `core/` 下的任何业务规则与数值（定价、折扣、匹配、门槛、校验、订单计时）。
- `mock/` 演示数据（它是生成物）。
- `i18n/` 下各文件里的文案措辞（文案经过产品裁定；发现错别字请登记，不要直接改）。
- 登录拦截逻辑 `services/auth.js` 的行为。
- 页面的布局、结构、颜色、字号（视觉与结构已冻结）。发现与预期不符请截图登记。
- 不新增页面、不删页面、不补做 `docs/W34_Status.md` 里列为「没做」的状态、不引入 npm 包或第三方组件库、不改成 TypeScript、不批量格式化或重命名。
- 不删除或跳过 `tests/` 里的测试；不为了让检查通过而修改 `tools/static_check.py`、`tools/smoke_run.js`。

**必须停下来问张坤的情况：**
- 修一个报错需要动上面「不可以改」的任何一项。
- 同一个报错有两种以上修法，且会影响用户看到的画面或流程。
- 需要 AppID、扫码、后台权限、支付参数、订阅模板 ID。
- 任何会产生真实费用或消耗额度的操作（微信手机号快速验证有额度，体验版同样消耗；支付一律按真实扣款对待）。

**编码约定（你的修改也要遵守）：** 数值只写在 `core/config.js` 与 `core/config-*.js`；文字只写在 `i18n/`；页面路径只用 `services/routes.js` 的常量；样式只用 `styles/tokens.wxss` 的变量；页面不直接读 `mock/`、不直接调 `wx.request`。

## 6. 任务二：探针工程（任务一完成后再做）

`probe/` 是另一个独立的小程序工程，用来在真机上确认几项有风险的平台行为（定位授权、隐私弹窗、订阅与支付的先后、键盘与安全区等），不是体验版，不用还原视觉。

- 导入 `probe/` 目录，同样先留基线、编译到 0 报错、记录全部报错原文。它同样没有在开发者工具里编译过。
- 按 `probe/README.md` 的「什么条件下能测什么」表，当前条件能测哪些就测哪些；条件不具备的项标「测不了」并写明缺哪个条件，不要想办法绕过。
- 每台手机测完，在探针的「结果汇总」页点「复制全部结果」，把文本原样放进回报。
- 探针和主工程共用一个 AppID 时，上传会互相覆盖开发版。先向张坤确认用哪个 AppID、先发哪一个。

## 8. 回报格式

按 `REPORT_TEMPLATE.md` 填写，一次任务交一份。要点：

1. **报错与警告一律贴原文**，附文件路径和行号。
2. **每一处改动一行**：文件、行号、改前、改后、原因、对应哪条报错。同时附 `git diff` 导出的补丁文件。
3. **没做的和测不了的单独列**，写明卡在哪个条件上。没验证过的不要写成「正常」。
4. **问题登记一条一行**：编号、页面、机型与微信版本、操作步骤、预期、实际、截图文件名、分类（缺陷 / 业务口径 / 平台做不了）、严重程度（阻塞演示 / 演示前要改 / 演示后再说）。
