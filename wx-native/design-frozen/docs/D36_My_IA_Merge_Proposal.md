# D-36 · 「我的」信息架构归并方案（供产品裁定，T7 前提）· VIS-REDESIGN-01A W5 · 2026-11-17

**为什么要裁**：仓库里有两套「我的」。M01（中央路由，`m01-rebaseline-01.js`）是用户在 Tab 栏看到的「我的」；`account.html`（独立页，`account.js`）是另一套含 18 个 view 的账户页，M01 的多处链接会跳到 account.html。WP05 把两者归入同一模板 T7，但**哪些视图保留、哪些合并、入口叫什么**是产品决定，不是设计决定（WP05 D-36）。下面是只读核对后的事实 + 三个可选方案 + 我的建议，张坤选一个（或改）即可开 T7。

## 2. 三个归并方案

### 方案 A · 单一「我的」（M01 为壳，account 的写视图并入 T7 二级页）【建议】
- Tab「我的」= M01 首页（profile 行 / 当前服务 / 我的仓位 / 我的记录 / 服务与权益 / 更多服务），结构不变。
- 二级页全部用 T7 模板（TopBar.page + 列表 / 表单段），共 **12 个**：我的订单（→O03）、我的需求（并入 account.needs 的修改 / 撤回 / 补充企业资料三操作）、报价方案、最近找仓、我的收藏、优惠与权益、消息、个人信息（并入 profile 的修改联系电话 / 验证手机号）、身份验证、入仓指引、联系顾问、关于迷你考拉（含推荐有礼一段）。
- 「租后服务」子视图取消：入口已在 O03 服务行（W4），M01「我的仓位」行直达 O03。
- 「运输需求」不保留为独立页：WP05 没有该页，运行时为占位（「服务与权益待确认」）；按 D-34 之外登记，等产品决定是否上线。
- account.html 退役，`centralPage` 重定向改为全部指向 M01 子视图。
- 代价：需合并两套数据绑定（线索写操作 / 联系电话写操作）到 M01 的 ctx；评审「载入订单样本」工具移到 `?review=1` 面板。

### 方案 B · 双层：M01 = 服务，account = 账户
- M01 只保留业务：当前服务 / 我的仓位 / 订单 / 需求 / 报价 / 最近找仓 / 租后服务。
- account 改名「账户与设置」，保留：个人信息 / 身份验证 / 收藏 / 优惠券 / 消息 / 推荐有礼 / 联系顾问 / 关于。入口 = M01 profile 行的「个人信息」。
- 代价：收藏 / 优惠券 / 消息 离开 M01 首页一层，与当前 M01 「服务与权益」块冲突，用户要多走一步；两套页面仍然并存（只是分工清晰）。

### 方案 C · 维持现状，只统一视觉
- 两套页面都按 T7 重绘，链接关系不动。
- 代价：重叠功能（收藏 / 优惠券 / 消息）要画两遍并长期维护两套；WP05 §4 硬门禁「同一组件同一数据」在跨页时无法保证；不建议。

## 3. 建议与需要裁定的点
- **建议方案 A**。理由：仓库自身已经在把 account 的订单 / 租后视图重定向到中央路由（1.2），方案 A 只是把剩余 7 个 account 视图收完；T7 一个模板承接 12 个二级页，与 WP05 的组件复用矩阵一致。
- 需要裁定：① 选 A / B / C；② 「运输需求」是否保留为页面（A 中默认不保留）；③ 「推荐有礼」是否保留（运行时注明「暂无经核定的推荐奖励」，A 中并入「关于迷你考拉」一段，不单独成页）；④ 「报价方案」与「最近找仓」是否合并为一个「找仓进度」子视图（两者都是需求态的派生，H01 需求卡已表达；A 中先保留两项，可合并）。
- 裁定后 T7 范围：M01 首页 17 个 policy 状态（与 H01 共用 derive）+ 12 个二级页 + OH01 订单记录 + 账号表单抽屉（联系电话 / 身份资料），预计采样 ≈ 90 次 × 2 视口。
